# 运动控制 / 九点标定岗位 · 面试问答准备

> 配套项目：`MotionCalibrationStudio`（本仓库）。回答尽量给「结论 + 依据 + 我在项目里怎么做的」。

## A. 运动控制类

**A1. 雷赛 / 固高 / 凌华 / 正运动的卡你用过哪家？差异在哪？**

差异集中在四点：① 函数命名与语义（正运动的"轴号"从 0 起且有虚拟轴概念，固高按轴号分组，雷赛多为 0 起）；② 回零方式配置（各家对「原点开关 + Z 相信号 + 限位回找」的配置项名称和顺序不同）；③ 错误码体系；④ 点动接口是否自带速度斜坡。

它们真正有差异的其实只有十几个动作（连接/使能/设参数/绝对定位/相对定位/点动/回零/停止/读状态/读写 IO）。我把这些定义成 `IVendorCardApi`，差异全部收敛在适配器里，状态机、等待到位、多轴同步、软限位这些通用逻辑只写一份。

**A2. 为什么软限位要在上位机也拦一道？**

控制器软限位触发后一般要清报警、重新使能，操作工不一定知道怎么恢复，往往就把设备停了。上位机在**下发指令前**判断目标是否越界，直接抛业务异常并给出可读提示，是最省事、最不易出事故的做法。控制器侧的软限位照设，作为第二道防线。

**A3. 梯形速度曲线和 S 曲线怎么选？**

梯形（匀加速-匀速-匀减速）计算简单、参数只有加速度/减速度/最大速度，绝大多数点位运动够用。S 曲线（加加速度受限）能显著减小启停冲击和机械振动，适合高速、大惯量或对定位稳定性要求高的场景，代价是参数多一个 jerk 且规划复杂。

我在项目里实现了梯形曲线，并处理了**行程不足时自动退化为三角形曲线**——这是实际最常踩的坑：行程短的时候如果还按梯形算，会算出一个永不到达的匀速段，导致曲线自相矛盾。

**A4. 点动（Jog）要注意什么？**

三件事：① **必须成对**，按住走、松开停，App 崩溃或窗口失焦也要停（我在界面上把「停止点动」做成独立按钮 + 状态变化时自动停）；② 点动的速度要与自动运行的速度分开配置，手动时用低速；③ 点动期间要禁止其他运动指令下发，否则会出现两个来源同时写同一个轴的目标位置。

**A5. 急停（E-Stop）和暂停（Hold）的区别？各自的恢复流程？**

- 暂停：减速停止、保持使能、保持当前位置，恢复时从断点继续。**恢复路径是"继续"。**
- 急停：立即停止（可能带机械抱闸），切断使能，机构失去保持力矩，必须排查安全风险后**重新初始化**（回零重建坐标系）。**恢复路径是"重新初始化"。**

这两条恢复路径完全不同，所以状态机里必须是两个不同的状态。我在实现时踩过一个坑：急停时既切了 `EmergencyStop` 状态又发了一条 Safety 报警，结果报警状态把急停状态覆盖掉了，现场就分不清是"急停"还是"普通报警"。修法是急停时报警但**不做状态迁移**。

**A6. 多轴联动和依次运动的区别？**

联动（`MoveAbsoluteAsync(MotionPose)`）是**同时**下发各轴目标再统一等待到位，走的是矢量路径，X 和 Y 同时到；依次是 X 走完再走 Y，走的是直角折线。做对位、插补必须用联动，否则轨迹是折线，会多花一倍时间，而且中间点可能撞上工装。

**A7. 什么叫"到位"？只看控制器的 in-position 位够不够？**

不够。控制器的 in-position 只是「进入到位窗口」，此时还可能有残余振动。稳妥的判据是：**控制器到位位 + 速度归零 + 延时稳定（settle delay）**。我在 `WaitInPositionAsync` 里同时判到位与速度，另外在拍照前加了几十毫秒的 `SettleDelayMs`——这个延时对视觉测量的重复性影响非常明显。

**A8. 跟随误差（Following Error）怎么用？**

跟随误差 = 指令位置 − 实际位置。稳态时它应该很小；如果持续变大，说明伺服增益不够、机构卡滞、或者发生了丢步。它是**在线诊断伺服与机构状态最直接的指标**，所以我把它直接做成一列显示在界面上，而不是藏在日志里。

**A9. 脉冲型和总线型（EtherCAT/CanOpen）控制卡的区别？**

- 脉冲型：上位机/卡发脉冲+方向给驱动器，接线简单、延迟确定，但轴数多时布线困难、无参数回读。
- 总线型：EtherCAT 主站周期下发 PDO、读 SDO，可回读驱动器参数与状态字，支持分布式时钟同步（多轴同步精度可到微秒级），是现在多轴设备的主流。

EtherCAT 的关键概念：主站/从站、ESI 描述文件、PDO 映射、CoE（基于 CANopen 的应用层协议）、分布式时钟 DC、以及**周期时间**（常见 1ms/500us）。上位机侧还要处理「PDO 数据与控制卡本地轴对象的映射与同步」。

**A10. CanOpen 的 PDO 和 SDO 区别？**

PDO（过程数据对象）是**周期性、实时**的，一问一答或一发多收，用来传控制字/状态字/目标位置；SDO（服务数据对象）是**非周期、带确认**的，用来读写参数对象字典。原则：实时量的走 PDO，参数配置走 SDO（且只在上电/使能前做）。

**A11. 伺服和步进怎么选？伺服"三环"是什么？**

步进便宜、低速力矩大、结构简单，但高速易失步且无反馈；伺服有编码器闭环，动态响应好、不过载失步、可回读状态。伺服三环从内到外：电流环（转矩，最内最快，kHz 级）→ 速度环 → 位置环（最外最慢）。上位机通常只与位置环打交道，调参主要由驱动器完成。

**A12. 回零为什么要先找原点开关再找 Z 相？**

只用原点开关，回零精度受开关重复性和接近速度影响（毫秒级开关延迟 × 速度 = 毫米级误差）。加上编码器 Z 相后，最后一段以低速找 Z 相跳变，位置由编码器零点确定，重复精度可以做到编码器分辨率量级。

**A13. 上位机怎么保证「一次只有一个运动指令在跑」？**

两个层面：① UI 层按钮的可用性由状态机统一决定（未就绪时点动/定位按钮是灰的），我做了统一的 `RaiseCommandStates()` 在状态变化时重算；② 命令层做互斥——异步命令执行期间不允许再次进入（`IsRunning` 标志 + `CanExecute` 返回 false）。设备软件里"同一个动作被连点两次"（比如连点两次回零）是非常典型的事故来源，必须在命令层就挡住。

**A14. 上位机的界面刷新和后台通信怎么隔离？**

状态轮询跑在后台线程（本项目默认 30ms），通过事件广播；界面侧必须切回 UI 线程再改绑定数据。WPF 里 `ObservableCollection` 被后台线程修改会直接抛「ItemsControl 与它的项源不一致」并可能把进程干掉。

另一个坑更隐蔽：**在 `CollectionChanged` 事件里同步调用 `ScrollIntoView` 会造成 ItemContainerGenerator 可重入，同样触发上面这个异常**。正确做法是用 `Dispatcher.BeginInvoke(DispatcherPriority.Background, ...)` 延后一帧再滚。我在做日志自动滚动时实机崩过一次才发现。

**A15. 设备软件的日志要求？**

① **带毫秒时间戳**（排查时序问题全靠它）；② 后台线程也能安全写；③ 分级（调试/信息/成功/警告/错误）并在界面上用颜色区分；④ 能一键导出成文本，现场直接发给供应商。

## B. 九点标定 / 视觉类

**B1. 九点标定的原理讲一下。**

相机随平台移动、Mark 固定不动。平台走到 3×3 网格的 9 个位置，每个位置拍一张图，提取 Mark 的像素质心，于是得到 9 组 (机械坐标, 像素坐标)。用这批点拟合「像素 → 机械」的映射（一般用仿射或单应），再用它的逆把"想让 Mark 落在哪个像素"换算成"平台该走到哪个机械坐标"。

**B2. 为什么是九个点？三点、五点不行吗？**

仿射有 6 个未知数，理论上 3 个点就够（6 个方程）。但：① 3 点无法评估残差，标完不知道准不准；② 单点测量误差会直接变成参数误差，没有任何平均作用；③ 9 个点有 18 个方程解 6 个未知数，最小二乘能把随机噪声压到约 0.8 倍；④ 3×3 网格顺带覆盖了视野的边角，能暴露镜头畸变和运动平台的直线度问题。

所以九点不是为了"解出来"，是为了"能评估、能抗噪、能覆盖"。

**B3. 标定精度取决于什么？**

四件事，重要性从高到低：
1. **Mark 的定位精度** —— 用灰度加权质心（不是二值质心），能做到 ±0.05px 量级；
2. **示教行程** —— 行程越大，同样的像素误差对应更小的机械误差（相当于放大了杠杆）；
3. **平台重复定位精度** —— 这是硬约束，标定只能平均掉随机误差，平均不掉系统误差；
4. **标定点布局** —— 共线或过于集中在中心会让方程病态。

**B4. 为什么一定要做坐标归一化？**

像素坐标量级 1e2，毫米量级 1e1，两列量级差 10 倍以上，设计矩阵条件数会被放大好几个数量级。Hartley 归一化的做法是：把每组点的质心平移到原点、平均距离缩放到 √2，用归一化后的坐标求解，最后把变换合回去（`T⁻¹·A·S`）。

效果可验证：我做了对比测试，归一化后九点仿射设计矩阵的条件数是 **1.076**；测试里专门有一条断言守护它 `ConditionNumber < 10`。

**B5. 为什么用 QR 不用正规方程？**

`AᵀA` 会把条件数平方，精度直接损失一半有效位。更关键的是工程上的理由：**QR 能给出秩的信息，正规方程不能**。标定点共线（操作工抄错、或者只标了一条线）时，QR 分解会出现极小的对角元，可以明确报「设计矩阵秩亏」；正规方程只会返回一堆看起来正常其实是垃圾的参数。

**B6. 留一交叉验证（LOOCV）是干什么的？**

RMSE 只说明拟合得好不好，不说明对没见过的点准不准。参数越多的模型训练残差一定越不差，所以只看 RMSE 必然选到最复杂的模型。

LOOCV 每次留出一个点、用其余 8 个点重新标定，再预测被留下的点。本项目的实测：

| 模型 | 训练 RMSE | 留一 RMSE |
|---|---|---|
| 仿射 | 0.004238 mm | **0.005782 mm** |
| 单应 | 0.003771 mm | 0.005692 mm |
| 二次多项式 | **0.002929 mm** | 0.006745 mm |

二次多项式训练最好、留一最差，典型过拟合。程序据此标记「疑似过拟合」并建议降级用仿射。

**B7. 仿射和二次多项式怎么选？**

仿射 6 参数（平移+旋转+各向异性缩放+剪切）覆盖相机正常安装的全部情况，抗噪最强，**优先用**。二次多项式 12 参数能吸收镜头径向畸变，视野大时更准，但自由度太多、容易过拟合噪声，只有留一误差明确优于仿射时才值得用。

判据我写在程序里：`IsOverFitting = LeaveOneOut.MeanError > TrainingRmse * 2`。

**B8. 单应什么时候用？**

相机有安装倾角、或者标定面与运动面不平行时，图像存在透视形变，仿射吸收不了。单应多两个透视分量（h7、h8），可以补偿。判断方法：看仿射标定完的残差是否**呈规律性分布**（而不是随机的），以及单应的透视分量是否显著大于 0。

**B9. 标定做完怎么判断能不能投产？**

我给了一个多指标的评估：RMSE/平均误差/最大误差 + 条件数 + 留一误差 + 逐点残差 + 反解参数核对。

最实用的是最后一条：把反解出来的**像素当量**和**相机安装角**打到报告里跟标称值对照（本项目实测 23.9997/23.9924 px/mm，真值 24；安装角 1.7305°，真值 1.7°）。如果标定整体跑偏，这两个数会先露馅。

另外逐点残差里**单个点超过 3×RMSE 就标红**——那是"这个点采坏了"（Mark 识别跳变、机械振动、光照突变），不是模型不好，重采那一个点就行。

**B10. 残差图怎么看？**

- 残差向量**整体朝同一个方向** → 系统偏差：标定参数有偏、机构反向间隙、或者 Mark 是斜的；
- **某个点单独跳出去** → 该点采集异常；
- **呈环形/蝶形分布** → 镜头径向畸变没被模型吸收，换二次多项式；
- **无明显规律、纯粹随机** → 正常，量级由视觉噪声决定。

我在界面上把残差向量放大 200 倍画出来（并在图例上明确标注了放大倍数）——残差常常是亚微米级，原比例根本看不见。可视化可以放大，但标注必须诚实。

**B11. 为什么标定中心选 Mark 的位置而不是平台原点？**

因为相机随平台移动、Mark 固定。如果把标定网格的中心放在平台原点，Mark 可能根本不在视野里。正确做法是先把平台移到 Mark 正下方（相机视野中心对准 Mark），以这个位置为原点铺 3×3 网格，这样 9 个点都落在视野内且最大化利用了像素分辨率。

**B12. 视觉定位怎么做到亚像素？**

灰度加权质心：对分割出的连通域，用 `Σ(I·x)/ΣI` 求质心。二值质心只能到 ±0.5px（受像素边界量化影响），灰度加权利用了目标的灰度分布，能做到 ±0.05px 量级。前提是光照稳定、目标对比度足够。

再进一步可以用模板匹配 + 亚像素插值（Halcon 的 `find_shape_model` 就能到 1/40 像素），或者对边缘做拟合并求交点。

**B13. 光照变化怎么处理？**

① 用 Otsu 自动阈值而不是固定阈值；② 关键设备用同轴光/环形光把光照固定下来，比算法补偿可靠得多；③ 用「面积 + 圆度」做几何过滤，把光照变化引起的噪点挡掉；④ 输出置信度，低于阈值直接判失败而不是硬算一个坐标。

**B14. 对位为什么要闭环？一次补偿不到位吗？**

理论上模型准一次就够，但现场有反向间隙、伺服整定误差、镜头畸变残差、视觉噪声，单次补偿残差通常在几微米到几十微米。闭环后实测 **1 次补偿即收敛到 0.0057 mm，收敛比 132:1**。而且闭环自带验证：最后那次拍照的残差就是交付精度的直接证据。

**B15. 对位时最怕什么？**

**视觉误识别导致补偿量离谱。** 基板上如果有其他圆形特征（螺丝孔、Pad），定位算法可能锁到它上面，算出来的补偿量可能是几十毫米——直接执行就是撞机。

所以护栏比算法重要：**初始偏差超过安全上限时直接拒绝移动，宁可停机让人来看。** 另外还要加迭代上限（默认 4 次）、置信度阈值、以及逐次记录像素坐标/平台位置/补偿量/残差/置信度形成可追溯记录。

## C. C# / 架构 / 设计模式类

**C1. 这个项目用了哪些设计模式？**

| 模式 | 用在哪 |
|---|---|
| 策略 Strategy | `IVendorCardApi` 多厂商实现、`ICalibrationModel` 三种标定模型 |
| 模板方法 | `MotionControllerBase` 定义流程骨架，子类只填厂商原语 |
| 适配器 Adapter | `ZmotionCardApi` / `GoogolCardApi` / `LeadshineCardApi` 把三家 SDK 适配成统一接口 |
| 观察者 Observer | `StatusUpdated` / `AlarmRaised` / `StateChanged` 事件 |
| 状态 State | 控制器状态机 |
| 工厂 Factory | `CalibrationModelFactory` 按枚举创建模型 |
| 值对象 Value Object | `Point2D` / `Matrix3x3` / `AxisId`（不可变，带运算符重载） |
| MVVM | 界面层 |

**C2. 为什么不用 CommunityToolkit.Mvvm / Prism？**

这套上位机只有 3 个界面，`ObservableObject` + `RelayCommand` 加起来不到 120 行就够用。多一个依赖就多一个现场部署和版本升级的变量 —— 工控机的软件维护成本远高于开发成本。反过来说，如果界面数量上到几十个、需要模块化和导航，我会引入框架。

判断标准是**复杂度是否已经超过了自研的成本**，而不是"流行什么用什么"。

**C3. 为什么把软限位拦截做成抛异常而不是返回 bool？**

因为"目标位置越界"是调用方**必须处理**的情况，不是可忽略的返回值。用异常能保证不会被静默忽略；而且可以携带结构化信息（轴、目标值、上下限），界面拿到后能直接给出可读提示。返回 bool 的话，很容易被写成 `_ = Move(...)` 然后把越界指令发下去。

**C4. 异步命令为什么要有 IsRunning 互斥？**

`async void` 的事件处理器可以重入。用户在设备动作期间连点两次「回零」，就会有两个回零流程同时在跑，互相覆盖目标位置 —— 典型的撞机来源。所以在命令层用 `_isRunning` + `CanExecute` 挡住，比在业务层到处加锁更简单可靠。

**C5. 你提到过 EF Core 的坑，说说？**

（这个是我在另一个 MES 项目上的真实经历）EF Core 对"通过导航集合发现、主键已经有值"的新子实体会判定为 `Modified` 而不是 `Added`，于是生成 `UPDATE ... WHERE Id=`，影响 0 行 → 抛 `DbUpdateConcurrencyException`。原因是实体主键初始化器给了 `Guid.NewGuid()`，新实体的主键不是默认值。解法是子实体一律**显式 Add**，且对已跟踪的实体不要再调 `Update(entity)`。定位手段是 `DbContextOptionsBuilder.LogTo(...)` 把真实 SQL 打到文件里看。

**C6. 大数据量下怎么保证查询性能？**

先查行数和索引再写 SQL；千万行以上的表必须带索引条件收窄；聚合用 `GetDataTable` + 手动映射而不是 ORM 实体化（减少装箱和反射开销）；超时保护要显式设置（默认无限等待会卡死界面）。我实际处理过 23 亿行的测试数据表，改成主键点查 + hint + 显式超时后稳定在秒级。

**C7. 说说你的单元测试策略。**

核心原则：**能自动验证的绝不用人盯着看**。

- 纯计算（标定、线性代数、速度曲线）→ 单元测试 + 解析解对照；
- 依赖硬件的行为 → 用一个**行为模型**代替（仿真卡不是 mock，有真实的梯形曲线、跟随滞后和噪声），这样测试才有意义；
- 全流程 → 端到端测试，断言可量化的精度指标（RMSE < 0.02mm、对位误差 < 0.01mm、反解参数与真值相对误差 < 1%）。

如果只断言"不抛异常"，那测试是没价值的。断言必须是**物理量**。

**C8. 这个项目你觉得还能怎么改进？**

- 标定点位可配：现在固定 3×3，`NinePointTeachingOptions` 已支持自定义顺序与行程，扩到 5×5 或 12 点只需改配置；
- 多相机：`ICamera` / `IVisionLocator` 都是接口，多实例注册即可；
- 带旋转轴的对位：`MoveProfile` 已支持旋转轴（度/秒），R 轴参与 `MotionPose` 后就能做角度补偿；
- 标定漂移监控：定时拍标准 Mark，用现有评估管线判断残差是否变大，超阈值提示重新标定；
- 接 MES 做设备能力（Cpk）追溯。

## E. 演示建议

面试时如果对方允许带电脑，直接跑：

```bash
dotnet test  tests/MotionCore.Tests          # 62 个测试，先证明工程能力
dotnet run --project src/MotionCore.App -- --demo
```

`--demo` 会在一分钟内自动跑完：初始化 → 九点示教 → 标定解算 → 三种模型对比 → 建立对位基准 → 故意偏移 → 自动对位收敛，并把每一步的可量化结果打进日志。

重点讲三段：
1. **残差可视化**（整体偏 = 系统偏差 / 单点跳 = 采坏了 / 环形 = 镜头畸变）；
2. **三模型对比表**（训练最好、留一最差 = 过拟合，所以只看 RMSE 选不出模型）；
3. **安全护栏**（初始偏差超限直接拒绝移动，宁可停机）。
